# TestFramework 项目评估（2026-10-15）

基线：`main @ 13d3128`（v0.5.2）加工作区未提交的改动，即 [2026-10-10 评估](functional-completeness-evaluation-2026-10-10.md)"本轮已落实"的三项：单位表扩充与可注册、序列级 `cleanup`、表达式位运算与字典取值。评估开始时本机 `dotnet build -c Release` 0 警告，`dotnet test` 447 个用例全部通过；本轮修复后为 455 个，全部通过，0 警告。

本文主要审查这批未提交改动，并重新看一遍整体架构。功能矩阵见 10-10 那份，这里不重复。

## 总体结论

整体架构已经成型，质量很高。未提交改动的主体是对的，但新加的序列级 `cleanup` 作为"安全收尾"，有三种情况会让它没有执行完。这些问题已在本轮修复，见下文"本轮已修复"。剩下的问题集中在两处：单位表做成了进程级可变全局状态；运行器类过大。

## 做得好的地方

- **分层清楚**：Abstractions（契约）/ Core（执行）/ SequenceYaml（读写与校验）/ UI 契约。框架本身不带界面，宿主 BMS-TEST 通过 NuGet 引用这几个库。
- **宁可拒绝也不猜**：单位不认识就判 `Inconclusive`；大小写匹配有歧义时不替用户选；位运算遇到小数直接报错，不截断；位运算优先级取 Python 的规则，`${faults} & 0x04 != 0` 按直觉成立。新代码一直坚持这个原则。
- **安全默认值**：有步骤被隔离时跳过清理；取消后有清理宽限；清理失败后停机；结果里能追溯插件版本和当时的限值。
- **测试和文档跟得上**：测试代码约 8.3k 行，占全仓 20k 行的四成以上。README 承诺的行为和代码一致；注释和文档普遍写了"为什么"。

## 未提交改动审查

### 已修复

1. **一个清理步骤出错，后面的清理步骤全都不跑。** 步骤 `onError` 默认是 `Stop`，`RunSectionAsync` 遇到 Error 就退出。于是"停充电机"一出错，"断开接触器"就不会执行，结果里也不会记成 Skipped。原有用例没发现，因为测试的 `Step()` 辅助方法把所有步骤都设成了 `Continue`。我写了临时用例，确认了这个现象。
   - 修复：清理段（测试项的和序列的）总是跑完每一步；清理段里第一个非 `Continue` 的决定仍决定清理段之后怎么走。测试项清理里有 `stop` 步骤出错时，清理段跑完，序列照样停止。
2. **被调用的子序列，自己的 `cleanup` 被悄悄丢掉。** `RunCallAsync` 只跑 `callee.Items`，校验器也不提示。我写了临时用例，确认了这个现象。
   - 修复：子序列的 `cleanup` 在调用结束时执行，不管它的测试项怎么结束（包括取消）；在子序列的变量作用域里执行，作为调用项的最后一个子项 `$cleanup` 记入结果；它的 `Fail` / `Error` 就是这次调用的结论。
3. **清理执行中途被取消，剩下的清理步骤不执行。** 序列 `cleanup` 用的是调用方的 token，中途被取消后，剩余步骤既不补跑，也不被记录。测试项 `cleanup` 的情况相同：`RunCleanupAfterCancellationAsync` 只要已有清理结果就直接返回。操作员恰恰可能因为收尾太慢才按停止。
   - 修复：被打断的那一步记为 `Cancelled`，其余步骤在共用的宽限窗口里继续执行。本来就在宽限 token 上执行、宽限到期的，不再重试。
4. **序列 `cleanup` 判 `Inconclusive` 的步骤被算作 `Pass`。** 测试项本身对非判定来源步骤的 `Inconclusive` 也不计入，这是有意的：测试项有 `verdictSource` 负责判定。但序列 `cleanup` 没有判定来源，步骤本身就是判定。"接触器电压 < 1 V"因为单位不认识判 `Inconclusive` 时，不应显示为通过。
   - 修复：步骤里有 `Inconclusive` 时，清理段判 `Inconclusive`，序列结论也随之为 `Inconclusive`。

新增 8 个用例（`SequenceCleanupTests`），逐一覆盖以上四条。README、ARCHITECTURE 与 `TestSequence.CleanupSteps` 的注释已同步更新。

### 未修复，建议后续处理

5. **单位表是整个进程共用、可随时修改的全局表，结果会随注册时机变化。**
   - 文档建议驱动"在构造函数里注册"，但构造发生在创建资源时，而校验在运行前就做完了。于是校验器会对驱动本来认识的单位报"未知单位"警告：校验结果取决于这个进程有没有创建过该资源。
   - 不区分大小写的回退会随注册的单位而变：现在 `S`（西门子）会被当成秒 `s`；以后有人注册 `MW`，原来能用的 `mw` 就会因为有歧义变成 `Inconclusive`。
   - 测试之间也会通过这张全局表互相影响。
   - 建议：让插件在加载时声明自己的单位，比如放进插件描述里，由 `PluginRegistry` 汇总；校验器和运行器读同一份声明。`Register` 留给宿主在启动时使用。
6. **字典下标的含义变了，旧写法会报错。** 以前字典进入表达式时会变成值列表，所以 `${signals}[0]` 能按位置取值；现在会报错。这是破坏性变更，0.6.0 的变更说明里要写明。

## 结构性风险

- `TestSequenceRunner.cs` 现在约 1740 行，`TestSequenceValidator.cs` 约 1100 行。流程控制、重试、循环、调用、清理、结论判定、插件执行门、资源租约都在同一个类里。每加一个功能，就在同一个类里多一组分支、多一种"这里也要处理取消"的路径。本轮的第 1、3 条，本质上都是"新路径没继承旧路径的某条规则"。
- 建议在 0.6 之后把"段执行（含取消与宽限）"和"结论聚合"拆成独立组件，否则后面的运行时控制（暂停、单步、从某项开始）会很难加进去。

## 宿主侧注意

BMS-TEST 的 `RunProgressModel.FindOrAdd` 按测试项 id 全局查找节点。子序列的测试项 id 只在它自己的文件里唯一，本来就可能和调用方的 id 重名；现在子序列的 `cleanup` 固定用 `$cleanup`，只要调用方和子序列都写了 `cleanup`，就一定会重名。后到的序列级 `$cleanup` 会复用子序列 `cleanup` 的那个节点，结论显示的位置就错了。

宿主应当按树路径（父节点加 id）索引节点，而不是只按 id。这不影响运行结果和结果文件，只影响进度树的显示。

## 后续落实（同日）

**第 5 条已完成：单位改由插件声明。** 用例从 455 增至 472，全部通过，0 警告。

- 新增公开记录类型 `MeasurementUnit`。`TestStepPluginDescriptor` 与 `ResourcePluginDescriptor` 新增 `Units`。`PluginRegistry` 与 `ResourcePluginRegistry` 注册插件时，先把它声明的单位整批加入单位表（全有或全无），再登记插件。
- 声明与已有定义冲突的插件整个被拒绝，加载器把它记为加载失败。单位表因此在加载时就定型，校验器和运行器看到的是同一张表，不再取决于"这个进程有没有创建过某个资源"。
- `MeasurementUnits.Register` 保留给宿主在启动时使用，并新增整批登记的重载（全有或全无）。
- 不区分大小写的回退收紧为三条：
  - 两个单位只差大小写时不认（`mohm`）；
  - 开头的毫 `m` 与兆 `M` 互换时不认，不论表里有没有对应单位（`MW` 不再被读成 `mW`）；
  - 单个字母不认（`S`、`H`）。
  - 大小写不携带含义的写法照常可用：`OHM`、`khz`、`KWH`。
  - 原先的规则会把 `MW` 当成表里唯一的 `mW`，相差 10⁹ 倍，这是本轮发现并修掉的问题。
- **契约升到 1.2**：插件只要用到 `MeasurementUnit` / `MeasurementUnits` 或描述符的 `Units`，就会在 0.5.x 宿主上缺类型，因此必须声明 1.2，让旧宿主在加载时明确拒绝它。10-10 那份评估里"契约仍为 1.1"的说法据此更正。
