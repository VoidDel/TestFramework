# 插件工作进程设计（P2）

状态：**设计，未实现。** 本文是 `plugin-architecture-evaluation-2026-09-18.md` 第 4 条的落地方案。P0（参数 schema）与 P1（工位配置 + 会话级资源）已完成，它们确定了这一步的大部分形状，本文记录确定了什么、还剩什么没定。

## 为什么要做

框架当前的隔离是**合作式**的：取消后 100 ms 未退出即隔离该步骤，序列中止但资源保留。对纯托管步骤够用。

BMS 上位机接的是厂商原生驱动——CAN 卡、程控电源的 VISA 库。这类 DLL 的典型故障不是抛异常，而是**访问违例**或**死锁在 native 调用里**：

- `CancellationToken` 管不到——托管层根本没拿到控制权。
- 合作式隔离看不到——没有可以"不退出"的托管任务。
- 访问违例直接终止进程——操作员界面当场消失，正在充电的 DUT 无人看管。

进程外执行是唯一能挡住这两类故障的结构。工作进程崩溃时，宿主仍然活着，能把 DUT 置于安全状态并告诉操作员发生了什么。

## P0 与 P1 确定了什么

评估报告预判这两条会决定工作进程的形状。实际落地后：

**参数跨进程已经可行。** `StepParameterKind` 只有 `String`/`Integer`/`Number`/`Boolean`/`Enum` 五种，这个集合是刻意选的——它既是宿主能渲染的，也是能序列化过进程边界的。声明了参数的插件，其参数面已经是可传输的；`LoadSettings` 返回的 `object` 设置对象**不跨边界**，它在工作进程内构造和使用。

这条改变了原先的判断："跨进程要求参数可序列化，schema 化不再可选"——schema 化已经做完了，现在的问题变成：**未声明参数的插件不能进工作进程**。这是可接受的限制，也是推动插件作者声明参数的正向压力。

**资源必须跟着进工作进程。** 这是 P1 之后最清楚的一点。步骤通过 `context.Instruments.GetRequired<IPowerSupply>("psu")` 拿到的是**类型化的 CLR 对象**，它无法跨进程传递。因此资源插件必须与步骤插件在同一个进程里。

`StationResourceHost` 的两层作用域正好对应：

- **工位作用域**活在工作进程里，与进程同寿。这也解释了为什么工位作用域的重建语义要先定清楚——工作进程崩溃就是一次强制重建。
- **运行作用域**同样在工作进程里，由宿主通过命令控制其开始与结束。

宿主侧保留 `StationConfiguration`（纯数据，可序列化），工作进程按它建资源。宿主不持有任何资源对象。

## 边界

进程边界划在**步骤执行**这一层，不在插件加载这一层：

```
宿主进程                          工作进程
  序列运行器                        插件加载（ALC 规则不变）
  校验                              资源插件 + 工位/运行作用域
  界面、结果存储                     步骤插件
  StationConfiguration（数据）       ITestStepPlugin.ExecuteAsync
        │                                 │
        └────────── IPC ──────────────────┘
```

跨边界要传的东西，及其可序列化性：

| 内容 | 方向 | 状态 |
|---|---|---|
| `TestStepDefinition`（含已解析的参数） | 宿主 → 工作 | 可序列化（P0 之后参数受 schema 约束） |
| `TestSequence` / `TestItemDefinition` 上下文 | 宿主 → 工作 | 可序列化（纯数据模型） |
| 变量快照 | 双向 | 标量字典，可序列化 |
| `PreviousStepResults` | 宿主 → 工作 | `TestStepResult` 是标量 + 字典 |
| `TestStepResult` | 工作 → 宿主 | 同上 |
| `context.Log` 回调 | 工作 → 宿主 | 需要反向通道 |
| `IResourceScope` 查询 | —— | **不跨边界**，资源留在工作进程内 |
| `ITestStepPlugin.SettingsType` / 设置对象 | —— | **不跨边界**，工作进程内构造 |

## 待定项

以下几条还没有定论，是实现前要先回答的：

1. **传输与编码。** 命名管道 + 长度前缀的 JSON 是最省事的起点；需要先量一下每步的往返开销对产线节拍的影响。步骤本身动辄数百毫秒，IPC 开销大概率可以忽略，但需要实测而不是假设。

2. **崩溃后的 DUT 安全状态。** 这是最重要也最不确定的一条。工作进程死亡时 DUT 可能正在充电。宿主自己没有资源句柄（都在死掉的进程里），所以"把 DUT 置于安全状态"不能靠宿主直接操作设备。可能的方向：看门狗进程、硬件级的失效安全（继电器默认断开）、或工作进程持有的资源由 OS 在进程退出时释放到安全默认值。**这条必须在写第一行 IPC 代码之前解决**——否则做出来的隔离只是把崩溃从"界面消失"变成"界面还在但 DUT 仍然无人看管"，价值大打折扣。

3. **粒度。** 一个工作进程装全部插件，还是每插件一个？全部装一起实现简单，但一个原生驱动崩溃会带走所有步骤。按插件隔离更彻底，代价是进程数与资源共享的复杂度（两个步骤共用一个 CAN 通道时，它们必须在同一进程里）。倾向：**按工位资源分组**——共用资源的插件同进程，不共用的可以分开。

4. **契约影响。** 很可能是 2.0：`ITestStepPlugin.SettingsType` 暴露 CLR 类型，这在跨进程模型里没有意义；`IStepSettingsEditorPlugin.CreateEditor` 返回 Avalonia `Control`（第 5 条），编辑器必须留在宿主进程，与运行时插件彻底分家。需要确认能否让进程内与进程外两种模式共存于 1.x，只对声明了参数、且被配置为进程外的插件启用。

5. **取消与超时。** 进程外的好处是取消可以退化为强杀。需要定的是：强杀之后工位作用域必然重建（等同于 `Invalidate`），以及强杀与 `PendingStepsCompletion` 现有语义如何统一。

## 不做的理由（当前）

第 2 条尚无答案之前，实现 IPC 只是把故障模式换了个样子，不是真的解决问题。建议顺序：先回答 DUT 安全状态，再定粒度，然后才是传输层。
